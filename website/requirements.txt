# ── Transitively required by the bot service layer ───────────────────────────
# A web service should not need Discord's library, and this is not a real
# dependency of anything the website does. It is import coupling:
#
#   website/backend/routers/proximity_scoring.py:52
#     from bot.services.proximity_session_score_service import ProximitySessionScoreService
#
# That import is lazy (inside the handler) and the service itself needs nothing
# beyond logging + guid/colour helpers. But importing ANY submodule of
# bot.services runs bot/services/__init__.py, which eagerly imports 16 modules —
# including prediction_embed_builder (-> discord) and session_graph_generator
# (-> matplotlib). So the whole Discord/plotting layer is dragged in to reach one
# scoring class.
#
# Determined empirically, not copied from the root manifest: a venv built from
# this file alone fails on `import backend.main`, and these two are the only
# additions needed. Everything else the root manifest pins (trueskill, paramiko,
# Pillow, aiosqlite, watchdog, …) is either transitive here or genuinely unused
# by the web app. Verified: uvicorn reaches startup, /health, /api/status,
# /metrics, /api/proximity/leaderboards, /api/sessions and /api/skill/formula all
# return 200, `pip check` clean.
#
# The real fix is decoupling — making bot/services/__init__.py lazy, or moving
# the scoring service somewhere neutral. Both touch the bot's package layout and
# belong in their own change; note that bot/core/__init__.py pulls discord too,
# so a half-measure would not help. Until then this file must describe reality:
# prod's venv-web already HAS these installed (verified live), so the manifest
# was the thing that was wrong, and a rebuilt venv-web would have died on import.
discord.py==2.6.4
matplotlib==3.10.8
