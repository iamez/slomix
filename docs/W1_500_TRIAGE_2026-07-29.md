## Structural limitation found first

`routed_path()` (`website/backend/security_utils.py:29`) — used by the logging middleware
for every `→ METHOD /path` and `← METHOD /path → status` line via `safe_path` — returns
**only** `request.scope["path"]`, never the query string. So for any endpoint that takes
query parameters, `access.log` cannot tell you what parameters produced a given 500.

This is not "query strings are never logged anywhere," though — `_check_security()`
(`logging_middleware.py:275`) separately reads `request.scope["query_string"]` and attaches
it (truncated to 200 chars) as an `extra={"query": ...}` field on a `security_logger.warning`
call, but **only** when the query matches one of `SUSPICIOUS_PATTERNS` (SQL-injection-style
strings etc.) — none of the failures below are that. And even for a request that did match,
the query wouldn't actually appear in `security.log`'s rendered text: the active formatter is
`StandardFormatter` (`logging_config.py`), whose format string has no `%(query)s` placeholder
— only the JSON formatter renders arbitrary `extra` fields, and JSON logging is off by default
(`LOG_FORMAT_JSON` unset). So in practice, for the ordinary (non-attack-pattern) 500s this doc
investigates, the query string genuinely isn't recoverable from any log on this box today —
the security-logging path just isn't the reason, and doesn't contradict that conclusion.

## `prox-scores` and `player radar`: root cause identified, not just "not reproducing"

`docs/research/SMART_STATS_SESSION_SCOPE_REVIEW_AND_REMEDIATION_PLAN_2026-07-19.md` (§16.2-16.3,
§17.4) already diagnosed both of these from a live 2026-07-19 investigation — found on a second
pass through this doc after a reviewer pointed out the citation existed. Summary: the dev
`etlegacy-web` process had stayed alive since 2026-07-07 22:17 with zero restarts, so its
in-memory Python route handlers were still the July-7 version, while `StaticFiles` (which reads
the frontend off the mutable checkout on every request) served much newer JS, and some
request-time lazy imports pulled newer Python modules into the same old process. Concretely:

- **prox-scores**: the old handler expected `compute_prox_scores()` to return a `list` and ran
  `results[:limit]` on it; a lazy import pulled in the *new* v2 service, which returns a
  `dict` — `TypeError: unhashable type: 'slice'`, logged as `prox-scores failed`, matching this
  doc's original grep exactly.
- **player radar**: same mixed-revision cause, inverse symptom — the long-lived old route
  function indexed `prox_scores[0]` (list access) against the new dict result —
  `KeyError: 0`.
- Both docs are explicit that **current tracked source is already correct**:
  `website/backend/routers/proximity_player.py:178-204` already consumes
  `prox_result.get("players", [])`, not list indexing. "The issue is the live process, not a
  request to re-implement that current fix."

So: not reproducing today is expected and explained, not merely unconfirmed. The mechanism was
a stale long-running dev process mixing code revisions — a deploy-hygiene issue distinct from
the endpoint logic itself, and the historical prod side of that same investigation (§16.3
table) shows production stayed internally coherent throughout and never 500'd on either
endpoint for the same requests.

## `win-contribution` / `storytelling-completeness`: tested against a real session, not a placeholder

The original version of this doc tested with `session_date=2026-07-20`, which has **no
matching gaming session** in the local database — `resolve_story_scope()`
(`website/backend/services/session_scope.py:296-302`) 404s before the handler runs any of the
queries that historically failed, so that test proved nothing about the endpoint itself.
Re-tested with a real session pulled from the database:

Both 200 against a session that actually exists and actually exercises the query path. Still
not proof of a fix (no traceback survived rotation for either), but a materially stronger "not
reproducing" than the original placeholder-date test.

## Why "cannot reproduce" is still not "confirmed fixed" for the rest

`predictions/recent`, `win-contribution`, `storytelling-completeness`, and
`seasons/current/awards` have no surviving traceback (errors.log only retains back to
2026-07-27, past every occurrence) and no diagnosed root cause the way prox-scores/radar now
have. Per the task's own rule ("if you cannot reproduce, say so explicitly — do not record it
as fixed"): **not confirmed fixed, only not-currently-reproducing** for these four.
`leaderboards` has a specific attributed fix (#564). `prox-scores`/`radar` now have an
identified, documented cause (dev-process staleness) that is distinct from "unconfirmed."

## Recommendation

If a 500 recurs on any of these endpoints, the fastest way to get real parameters is the
client-side error reporting work in W4 (`POST /api/client-error` with **the failed request's
own URL**, not just the page URL — see that PR's fix for why page URL alone doesn't capture a
separate API fetch's query string). This doc doesn't change `routed_path()` itself: that
function is deliberately security-scoped (Host-header spoofing prevention) and logging query
strings server-side risks leaking session tokens or GUIDs into a file with looser retention
than intended; better to close the loop from the client side where the page already knows what
it asked for.
