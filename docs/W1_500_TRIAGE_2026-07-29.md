# W1 — triage of historical 500s (2026-07-29)

Task W1 from `docs/TASKS_FOR_SONNET_2026-07-29.md`. Method: pull every `→ 5xx` line
from `logs/access.log`, find the matching request/traceback, then replay live
against the local dev backend (`website/venv/bin/uvicorn backend.main:app`, already
running on `127.0.0.1:8000`).

## Structural limitation found first

`routed_path()` (`website/backend/security_utils.py:29`) — used by the logging
middleware for every `→ METHOD /path` and `← METHOD /path → status` line — returns
**only** `request.scope["path"]`, never the query string. So for any endpoint that
takes query parameters (all seven below do, or take none), the access log cannot
tell you what parameters produced a given 500. "Replay with the original failing
parameters" is only possible when an endpoint takes no parameters at all. This is
a real gap, not a triage inconvenience — see the recommendation at the bottom.

## Why "cannot reproduce" here is not the same as "fixed"

`prox-scores` is the one worth being precise about: it 500'd 8 times across nearly
4 months, most recently 2026-07-20, always with the same log signature
(`api.proximity | get_prox_scores:721 | prox-scores failed`, no traceback text
survives rotation). Between 2026-07-20 and today the file it lives in
(`website/backend/routers/proximity_scoring.py` / `services/prox_scoring.py`) had
five substantive commits, including a full `prox_score` v3.0 rewrite
(`e830b67e`, #556/#559) and a serving-layer correctness sweep (`ab2809de`, #548).
It is plausible one of those fixed the underlying issue, but since the exact
failing parameters were never logged, this is circumstantial, not proof. Per the
task's own rule ("if you cannot reproduce, say so explicitly — do not record it as
fixed"): **not confirmed fixed, only not-currently-reproducing** for every row
above except leaderboards (which has a specific attributed fix, #564).

## Recommendation

If a 500 recurs on any of these endpoints, the fastest way to get real parameters
is the client-side error reporting work in W4 (POST `/api/client-error` with page
URL, which for these proximity/storytelling pages includes the querystring the
frontend built) — that closes the exact gap found here. This doc doesn't change
`routed_path()` itself: that function is deliberately security-scoped (Host-header
spoofing prevention) and logging query strings server-side risks leaking session
tokens or GUIDs into a file with looser retention than intended; better to close
the loop from the client side where the page already knows what it asked for.
